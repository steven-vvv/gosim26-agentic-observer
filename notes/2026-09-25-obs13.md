# 实验记录：Fable 评估后的一轮（2026-09-25）

本文中的 `dist/` ZIP 和 `dist/portfolio/` 文件是当时的本地构建产物；它们可由文中命令重建，
不作为版本库输入保存。

## 外部评估要点（Fable 5.1 子代理，只读分析，简报见 `v3/runs/briefing.md`）

- 纯算法剩余空间不到 1 个点：46 场 obs12 比全知可行排程低 3.45%，其中信息差（标签全知约 0.3%、故障 / 新星全知、完美天气 +1.7%）约 2.5–2.7 个点。
- **最大的期望损失在平台耗时**：CPython 下规划占整场大头，平台稍慢就会降级（慢 1.5 倍 −0.11%、慢 2 倍约 −0.8%），重跑核验时还可能走出不同轨迹。
  建议把规划器用 numpy 向量化（可逐位一致），`requirements.txt` 装 numpy、装不上退回纯 Python，并先在 Playground 验证安装路径。
- 找到的两处结构性漏洞：寒潮期读数按事件归一化（估 +0.15–0.2%）；机会充裕的 REQUIRED 天区参与定价（估 +0.1–0.2%）。
  小项：plan_beta、λ 取末段平均、规划器计入故障、重规划 900 秒 / 推演 90 分钟。
- numpy 前向模拟器现在不值得做：可调的参数几乎都在噪声内，快 4 倍也撑不起系统搜索；更便宜的替代是租多核机器（逐字节一致）。
- 提交策略：第一天先交最可信的冻结版本并读平台日志（墙钟、是否降级、罚分）；组合里混入结构不同、期望相近的配置；
  最后一次提交不晚于 10-07 10:00 UTC；不要把平台报告里推出的隐藏天气、故障区、标签写回程序。

## numpy 规划器（逐位一致）

- `planner.py`：次梯度循环提成 `subgradient_python` / `subgradient_numpy` 两个函数，numpy 可用时走向量化路径。逐位一致的依据：
  约化收益逐元素 v − ticks·λ（乘、减顺序与原式相同，缺失的 (天区, 时段) 填 −inf）；argmax 取首个最大值，pairs 按时段递增
  （按夜、按时段顺序生成），与“严格大于才替换”选中同一时段；需求累加的是小整数 ticks；λ 逐元素更新。
- 验证：真实场景首次规划（300 次迭代，含“末 50 次取平均 λ”）两条路径的 μ 逐位相同（单元测试）；整场 comp-a-s101：
  CPython agent（numpy）与 PyPy agent（纯 Python）的 decisions.csv / score_report.json 逐字节相同。
- 耗时：CPython 下规划累计 866 秒 → 65.8 秒（556 次，快 13 倍）；平台上整场预计约 400 秒（时钟 3600 秒）。
- 每 100 次决策往 stderr 打一行累计墙钟与规划耗时，平台 agent.log 里据此读出机器速度。

## 寒潮期读数按事件归一化（标签，离线即真实）

寒潮是唯一只压低效率、又不闭站的 ALL 范围事件，单个事件内乘数不变，事件 id 在站点天气里。寒潮期按真实有效天气算事后期望，
读数 = 事件乘数 × 效率抖动 × 仪器侧。用同一事件此前读数的中位数 / 0.95 估计乘数、至少 3 个先验读数，读数除以乘数后：
普通 [0.893, 1.015]、红化 [0.721, 0.798]、新星 [1.334, 1.690]（P1–P99），仍互不重叠。

| 规则（46 场，obs12 的轨迹） | 红化 对 / 错 | 新星 对 / 错 | 每场 |
|---|---|---|---|
| 中位数 / 0.95，≥ 3 个先验读数（采用：红化 [0.73, 0.79]、新星 [1.30, 1.70]） | 25 / 1 | 34 / 2 | **+118.5** |
| 同上，≥ 5 个先验读数 | 21 / 1 | 32 / 2 | +105.4 |
| 截尾均值 / 0.95 | 21–24 / 0–2 | 32 / 1 | +112.0 |
| 事后用整个事件的中位数回头补报 | 26 / 0 | 35 / 8–9 | +103–107（故障分区拉低中位数，普通读数被当成新星） |
| 最大值估计乘数 | 11–12 / 592–635 | 19 / 0 | −1,865 ~ −2,003 |

估计乘数时排除疑似故障分区、新星阈值提到 1.33，结果不变。比 Fable 估计的 +0.15–0.2% 小，约 +0.06%。

## REQUIRED 参与定价：采用

机会充裕（视野内可行时段 ≥ 40 个、离可用期结束 ≥ 5 夜）的 REQUIRED 天区放进规划器，时段价值加上按开放率折算的 +1000
（在“收益 − μ”里大体抵消，只比时机）；机会少的维持一有窗口就拍；步长只按科学分定。
46 场 **+0.195%（标准误 0.041）**，33 场变好；基础分 +206、加成 +63、覆盖 +72；**零 REQUIRED 缺失、零 FLEX 缺额**
（32 个蒙特卡洛场景用的是真实决赛目录，eval 目录里那几块窄窗口天区都完成了）。

## 规划器计入故障：不用

已确认 / 疑似故障分区在修复前的时段价值乘以故障乘数：46 场 −0.002%（标准误 0.031）。

## plan_beta 0.9、λ 取末段平均：不用

- plan_beta 0.9（μ 打九折）：12 场 −0.40%（标准误 0.24），3 场变好，提前停止；β = 1 仍是最好的。
- 最后 50 次迭代的平均 λ 定价：20 场 −0.059%（标准误 0.084），9 场变好，提前停止。

## obs13 = obs12 + REQUIRED 参与定价 + 寒潮期标签归一化（+ numpy 规划器）

46 场相对 obs12 **+0.247%（标准误 0.045）**，34 场变好。基础分 / 加成 / 覆盖的增量（+206 / +63 / +72）与只开 REQUIRED 定价时
逐分相同（寒潮期标签不改变轨迹），上报奖励 +143.5、罚分 +9.8（寒潮期 3 次标签错报）；零 REQUIRED 缺失、零 FLEX 缺额。
程序包 `dist/observer-obs13.zip` 含 `requirements.txt`（numpy>=1.26）。

程序包验证（`v3/runs/verify-pkg.sh`，官方 runner，comp-a-s101，机器满负荷）：
- Python 3.12 + numpy（模拟平台按 requirements.txt 装好的环境）：总分 183030.963382，与 PyPy + 加速 runner 逐位相同；
  整场 644 秒、规划 135.6 秒（555 次），不降级。每 100 次决策一行的计时日志正常。
- 系统 Python 3.12（没有 numpy，纯 Python 回退）：这次机器上有 6 个进程，外推 2088 秒 > 50%，退回每小时重规划（339 次规划），
  轨迹因此不同（182,579.8）。两条路径本身逐位一致（CPython + numpy 对 PyPy 纯 Python 整场逐字节相同）；
  回退路径的耗时与 obs12 相同，平台装不上 numpy 时最坏退回每小时重规划。

## 寒潮期读数也作为故障证据（cold_faults）

归一化后的寒潮期读数走精确读数的故障逻辑（≤ 0.705 单次确认）。46 场相对 obs13 **+0.048%（标准误 0.031）**；
只有 9 场轨迹变化（故障发生在寒潮期的场景），其中 7 场变好，折合每个受影响场景约 +0.25%。
故障检出延迟中位数 14.9 → 2.9 小时、均值 14.0 → 9.5 小时，故障误报 2 → 2。机制清楚、没有额外误报，采用。

## 推演 90 分钟、每 20 分钟重规划：不用

- 推演 60 → 90 分钟（obs13-ro5400）：46 场 −0.075%（标准误 0.040），13 场变好。60 分钟是最好的。
- 每 30 → 20 分钟重规划（obs13-ev1200）：46 场 +0.008%（标准误 0.029），23 场变好，没有效果。

## obs14 = obs13 + 寒潮期读数作为故障证据

46 场相对 obs12：obs13 的 +0.247% 加上寒潮期故障证据的 +0.048%，合计约 +0.30%。冻结的 obs14 与 obs13-cf 在 4 个场景上逐位相同。
程序包：`dist/observer-obs14.zip`（含 requirements.txt）与 `dist/observer-obs14-stdlib.zip`（不带依赖的备用包）。

## 1. 完整项目与统一入口

完整项目从[参赛页](/compete)进入，支持公开 GitHub 仓库链接或不超过 50 MB 的私有 ZIP。语言不限，平台的 Python 运行器负责连接你的程序，不要求项目使用 Python。

平台固定源码版本、启动配置和适配文件，检查通过后由你审阅并确认。适配只提出接口文件，不会悄悄替换你的算法。模型调用不是必需的。

[最小完整项目示例](https://github.com/BH3GEI/observer-project-example)

## 2. 启动配置

项目根目录放置 `observer.project.json`，例如：

```json
{
  "schema_version": "observer-project-v1",
  "protocol": "jsonl-v2",
  "image": "python:3.12-slim",
  "working_directory": ".",
  "build": [],
  "run": ["python3", "agent.py"]
}
```

根据语言选择容器镜像和构建命令。`run` 和每条 `build` 命令都使用参数数组，评测时镜像会固定到具体摘要。不要把密钥写入配置或项目文件。

## 3. 每轮请求对应一个决策

项目持续运行，标准输入和标准输出均为每行一个 JSON 对象。日志写到标准错误，响应后立即刷新输出。

- `initialize`：公开配置和目录，不需要回复。
- `decision_request`：本轮快照和 `decision_sequence`，包含当前天气、可观测天区、请求、进度和已经发布的预报。
- `decision_response`：使用相同序号和 `protocol_version: participant-agent-protocol-v2`，返回 `observe` 或 `wait` 决策，可同时附带异常上报。完整结构见下方交互示例。

服务器记录本轮决策后才返回下一轮观测，提前提交未来序号会被拒绝。相同决策可以安全重试，已接受的决策不能替换。未来天气和异常答案保留在服务器。

一个 900 秒日历时隙不一定对应一个决策：曝光可以跨时隙，同一时隙内也可能有多个短曝光。请遵循返回的序号和游标。

## 4. 确认版本并评测

平台固定源码版本和启动配置，检查接口后交由你审阅并确认。确认后启动评测，每批运行全部指定场景，每次运行逐轮向服务器返回决策，不接受 CSV 上传。

## 5. 可选的个人模型 API

需要模型时请自备 API 和额度，平台不提供模型额度。凭证通过 HTTPS 加密传输，只在页面和请求内存中使用，不进入数据库、项目文件、运行结果或日志。不要把密钥放入仓库或 ZIP。

使用模型时，需要在「参赛」页填写支持 HTTPS 的接口、模型和密钥，并保持页面打开（包括自动适配期间）。关闭页面或断开连接会清除密钥，重新连接需再次填写。

确定性算法不需要密钥，解释写得更长不会增加比赛得分。

## 6. 随机题目与评分

每队每次新评测使用新的保密种子，公共目录、观测任务和评分规则保持固定，天气、事件和隐藏标签变化。同一次运行的基础设施重试保留原题。

三种固定参考算法按照预先确定的范围检查题目难度，范围外的题目不交给选手。上榜分为：

```
10000 × (原始分 − 全程等待分) ÷ (参考算法平均分 − 全程等待分)
```

全程等待为 0，参考算法平均为 10000，更强的算法可以超过 10000。校准减少题目差异，但不能保证每种策略感受到的难度完全相同。

每批包含全部场景，全部完成后才上榜；批次得分为全部场景校准分的平均值。每队取最高分的完整批次，不能拼接不同批次的场景最高分。原始得分组成仍可查看，具体评分、惩罚和同分处理见[规则](/rules)。

## 7. 结果与复现

结果包含决策、原始分与校准分、运行状态及日志。平台的私有复核记录保留种子、生成器版本、校准配置、源码版本和文件摘要，供主办方准确重建题目并重新评分。选手下载内容不包含未来数据和私有密钥。

请保留自己的源码版本、启动配置和复现说明。设计评价根据代码、运行记录和复现进行，与成绩榜分开。

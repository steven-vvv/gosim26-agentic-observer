# 正式赛新赛制下的现状评估（2026-09-25）

## 一、总体判断

**优势**
- obs14 是为"时间稀缺、天气隐藏、逐轮决策"设计的，这正是正式赛的设定。46 个决赛规模场景（含 32 个"真实决赛目录 × 自有天气"）上相对官方基线 A 类 +6.71%（+3.19% ~ +9.70%）、B 类 +7.65%（+5.47% ~ +10.03%），比全知可行排程只低 3.12%（0.25% ~ 6.71%），其中大部分是信息差。
- 用基线代替"参考算法平均"的校准分：A 类 10,599（σ 130）、B 类 10,687（σ 128）；一批（A、B 各一场平均）10,643（σ 89）；30 批取最好期望 **10,812**（P10 10,766，P90 10,868）。参考算法若比基线强 5%，全体数值降到约 10,190，但不影响相对排名。
- 时间保护实测有效（见第六节）：把时钟压到 700/550/420 秒（相当于平台慢 1.8×/2.4×/3.1× 或每轮往返 1–2 秒），三种降级都完整跑完、零罚分，损失分别只有 −0.25%、−1.01%、−1.83%。
- 确定性、纯标准库 + 可选 numpy，numpy/纯 Python/PyPy 三条路径逐位一致，核验复现有基础。

**主要风险（按期望损失排序）**
1. **协议/环境导致整批作废**：已确认 agent 遇到未知 `message_type`、未知 `schema_version`、未知 `protocol_version` 三种情况都直接退出（`agent_error`，该场景只有已提交动作 + 终局罚分）。新赛制的 `jsonl-v2` 是否有新消息类型未知。这是唯一能把一批打成零分的漏洞，修复成本一小时。
2. **构建阶段装不上 numpy**：纯 Python 路径整场 973 秒（空闲本机），平台若再慢 1.9× 就触发降级（−0.25%），慢 2.2× 触发每夜规划（−1%）。
3. **墙钟口径未知**：旧文档明确说时钟"包含快照序列化、你的思考时间与解析时间"；新赛制"服务器记录后才给下一轮"，往返是否计入未知。每轮 1 秒往返 ≈ 1,400 秒。
4. **异常规则对生成器漂移的脆弱性**：唯一能造成几个百分点损失的是"效率抖动下界变宽"导致红化误报（见第二节问题 4）。
5. **核验复现**：墙钟降级会让轨迹随机器速度变化，可能被判"无法复现"。

**预期名次**：82 队报名、81 队上墙，练习榜 26 队。练习榜上有真实在线 agent 且明显超基线的只有 BigP（dev-fortnight +33%）、fluvs（+32%）、DeepSky（+22%）、远地点（+4.6%）等几队，其余 kind=agent 的队与基线相同；CSV 榜首（AstroNJU、Pleiades 等）靠事后最优，在线实力未知。练习场景时间富余、比的是耐心，obs14 在那里只有 +8.9%，但决赛场景时间稀缺，"等好天气"策略吃亏。我的估计（以平台不出事故为前提）：**前 6 名（有奖）约 75–85%，前 3 名约 50–60%，第 1 名约 25–35%**；主要不确定性来自看不到其他队的决赛级实力，以及平台运行风险。

## 二、五个重点问题的结论

### 问题 1：新赛制下的目标函数

**校准分把天气方差压掉了九成**：原始分相对标准差 9.6%/10.2%，校准分只剩 1.2%。剩下的 1.2% 是"我们相对参考算法的优势随种子变化"，回归显示故障乘数从 0.4→0.7 约 +111 分（乘数越温和、基线越检测不到故障，我们的相对优势越大）、B 场景比 A 高 87 分，R² 仅 0.17，其余是特异噪声。

**均值 vs 方差**：`E[30 批最好] ≈ μ + 2.04σ_批`。σ_批 ≈ 89 主要来自种子，所有队都拿到这份"彩票红利"（约 +170 分 ≈ +1.6%）。理论上 1 单位 σ 值 2 单位 μ，但我们手里没有"不伤均值、只抬方差"的杠杆：用现有 15 个变体做混合提交的 bootstrap（analyze2.py），无论 15/15 还是 25/5 混合，E[max] 全部低于"30 批都交 obs14"（10,812），最好的 obs13-ev1200 混合也是 10,810–10,811。**结论：只优化均值，不做方差工程。**

**批次的边际价值急剧递减**：1 批 10,644 → 5 批 10,745 → 10 批 10,775 → 20 批 10,799 → 30 批 10,812。前 10 批贡献了 78% 的"取最好"收益，第 21–30 批合计只值 13 分。推论：(a) 第一天就要有能跑通的版本，比最后几批更重要；(b) 用 2–3 批做诊断几乎不花钱——只要诊断版本是正常的 obs14 配置，它们本身就是有效抽样；(c) 一批因平台事故作废的代价只是少一次抽样（≈ 13 分），**不是**那一批的低分本身——所以对"崩溃风险"可以比旧赛制宽容，对"均值"应更贪心。

**`dist/portfolio` 没有价值**：中性扰动的轨迹噪声（两场平均 σ ≈ 11）叠加到种子噪声（σ ≈ 89）上，30 批取最好只多 1.5 分；而每个新版本都要过平台"检查—审阅—确认"流程。旧赛制下"固定题目择优"的前提已不存在。**建议废弃，只准备 1 个主版本 + 1 个环境备用版本（PyPy 镜像或纯 Python）。**

### 问题 2：平台运行风险

实测数据（第六节有命令）：
- 消息体积：`initialize` 一行 **58.2 MB**（target_catalog 403,667 行）；普通 `decision_request` 447–470 KB（574–608 个候选）；夜首 1.08 MB；含每周发布 5.46 MB；一场约 700 MB 下行 JSON。本地管道读取 + 解析 initialize：CPython 0.8–1.0 秒、PyPy 0.6–0.7 秒，30 秒初始化预算没有问题——除非平台把 58 MB 走慢速网络。
- agent 峰值内存：CPython 334 MB、PyPy 290 MB，几乎全是没用到的 target_catalog。容器内存限额未知；解析后 `pop("target_catalog")` 可省约 250 MB。
- 逐决策耗时（官方 runner + CPython 3.12 + numpy，空闲本机）：决策循环 354 秒 / 1,404 次 ≈ 0.25 秒/次，其中 runner 快照生成约 0.17 秒/次（基线 agent 整场 232 秒即 runner 本身），agent 约 0.09 秒/次（规划 84 秒）。PyPy 下 agent 约 40 秒。

**逐轮往返 × 1,450 次**：以 CPython+numpy 计，projected = 380 + 1,400·r；r > 1.0 秒/轮触发第一级降级（−0.25%），r > 1.2 秒触发每夜规划（−1%），r > 2.3 秒即使关闭规划也会超时。agent 的外推用的是两次决策间的墙钟，**天然把往返算进去了**，这是保守的正确方向：若平台不计往返而我们计了，最坏白降级 0.25–1.8%；若平台计而我们不计，则是超时灾难。保持现状，但把 `time.process_time()` 一并打进 `decisions=N wall=… plan=…` 那行，第一批日志就能拆出"我们的计算 vs 往返 + runner"。

**numpy 的安装**：旧文档写"在时钟开始前用 pip 装进独立虚拟环境（最多 15 分钟）"、"平台运行允许联网"，新赛制大概率仍能联网，但没有确认。建议 **`python:3.12-slim` + 仓库内预置 wheel + 容错 build**：
```json
{"schema_version":"observer-project-v1","protocol":"jsonl-v2","image":"python:3.12-slim","working_directory":".",
 "build":[["sh","-c","pip install --no-index --find-links wheels numpy || pip install 'numpy>=1.26' || true"]],
 "run":["python3","-u","main.py"]}
```
（build 字段的确切形态以平台文档为准，示例仓库的 manifest 连 `build` 都没写。）预置 cp312 的 manylinux x86_64 + aarch64 两个 wheel 约 35 MB，在 50 MB 以内。build 失败也不阻塞，agent 自动退回纯 Python。备用方案 **`pypy:3.11-slim`**（Docker Hub 有官方镜像，64 MB，amd64/arm64，3 天前推送，PyPy 8.0.0）跑纯 Python，agent 部分约 40 秒且无依赖，`run: ["pypy3","-u","main.py"]`；本地已验证 PyPy 输出逐位一致。主备的选择在平台"检查接口"的预览日志里看 `plan #1 [numpy]` 还是 `[python]` 再定。

**容器速度与阈值**：5% 进度时的外推（383 秒）与实际整场（383 秒）一致，numpy 让开局开销很小，外推可信。50/60/85% 的阈值不必调；但降级目前是单向的，一次早期的短暂卡顿会让整场降级——加"外推回落到 40% 以下时恢复"约十行代码，低优先级。

**协议容错（必须做）**：
1. 未知 `message_type` / `schema_version` / `protocol_version`、`json.loads` 失败、缺 `decision_sequence`：记 stderr，不退出；带 `decision_sequence` 的消息一律回一个 `decision_response`（能解析就正常决策，不能就 fallback/wait），不带序号的忽略。
2. **重复序号幂等**：平台说"相同决策可以安全重试"，意味着同一序号可能再发一次。实测重复序号回复逐字节相同，但若首次回复带了 `reports`，重复时 `reported_tags` 已记录、reports 不会再带——响应不同可能被判冲突。缓存最近若干序号的响应原文，重复请求直接重放。
3. 回复的 `protocol_version` 改为回显请求里的版本（示例项目就是这样做的），未知时用 v2。
4. 解析 initialize 后丢掉 `target_catalog`。
以上都不改变决策，改完在 4–6 个场景上与 obs14 逐字节比对即可。

**"适配"可能改什么**：文档说只提出接口文件、不替换算法。我们自带 `observer.project.json` 后适配应为空操作。确认前逐项核对：镜像摘要、`run` 命令、`working_directory`、是否多出包装脚本、是否改了入口文件名。

**可复现性**：hash 随机化不影响（集合只做成员判断/求 min，且 CPython 与 PyPy 输出一致已证明无序依赖）；libm 末位差异在同一镜像摘要内不存在。唯一隐患是墙钟降级：建议 (a) 把当前规划模式写进 `reason` 字段，decisions.csv 自带解释；(b) 加环境变量 `OBS_DEGRADE_SCHEDULE="hourly@0.31,nightly@0.52"` 之类的重放钩子，核验方按 agent.log 里的 `projected` 行就能逐字节复现；(c) 在方法说明里写明这一点。numpy 路径只用时钟的 10%，正常情况下不会降级。

### 问题 3：算法本身的剩余空间

不建议再做算法改动。理由：46 场比全知可行排程低 3.12%，信息差约 2.5–2.7 个点，剩余 ≤ 0.5%，散在许多 ≤ 0.1% 的小项里（选档上限 0.03–0.05%、插值补报 0.01%、请求已全部完成、推演/重规划参数都在噪声内），每项验证要 25 分钟 × 多轮，且每次改动都是回归风险。1% 原始分 ≈ 96 校准分，而一次 `agent_error` 丢掉一场的全部分数。

**哪些稳健、哪些可能过拟合**：对偶价格规划、精确读数、REQUIRED 定价这些结构性收益在 32 个蒙特卡洛天气上逐场为正，稳健；`rollout_seconds` 3600、`plan_every_seconds` 1800、`refine_top_k` 12 这类参数的 ±0.1% 差异属于对本地 46 场的拟合，不必再动。校准分对天气好坏几乎不敏感（相关 +0.03），对故障乘数正相关（+0.27）——我们相对参考算法的优势在"温和故障（0.6–0.7）"场景最大，因为 kit 参考检测阈值 0.60 对这类故障永远检测不到而我们 0.705 单读即确认。这是结构性优势，不是过拟合。

### 问题 4：异常机制的泛化

阈值都来自公开的 eval-a/b `weather_config.json`/`score_config.json`/`tile_config.json`（抖动 [0.90, 1.00]、故障 [0.4, 0.7]、寒潮效率 0.68、nova 1.5、reddening 0.8、每场 1 次故障、10+10 标签），规则说"公共目录、观测任务、评分规则固定"，且 `make_scenario.py` 注释称隐藏场景"用同一生成器"。逐条评估漂移影响：
- **最脆弱：抖动下界变宽**（如 [0.80, 1.00]）。普通读数会落进红化区间 [0.71, 0.81] 的上沿，每次误报 −150；若 5% 的读数落进去，一场约 60 次误报 ≈ −9,000（−5%）。其他所有漂移（nova 因子变小、reddening 因子变大、故障区间变化）都只导致漏报，不导致误报——失败方向是安全的。
- 寒潮乘数用事件内读数中位数在线估计，对乘数变化稳健。
- 故障 `count` 若 >1：`single_fault` 会让第二次故障永不上报；但正确上报后有一次免费误报额度，所以"修复完成后遇到 ≥2 次同分区 ≤0.705 的精确读数就再报一次"期望成本为零。
- 故障 scope 非 REGION_SET 时 `fault_regions` 为空，退回自估乘数，可接受。

**建议的稳健化（1–2 天，含 46 场验证）**：把普通读数的经验分布用起来——前 50 次精确读数的主簇下界若低于 0.85，就把红化上沿收紧到"主簇下界 − 0.03"并要求两读；nova 同理用主簇上界。这是保险，正常分布下与 obs14 逐位相同。**开赛第一批就打开 `log_reads`**（纯日志、不改状态，30 场总分逐位相同），agent.log 会给出每次读数的比值，当天就能判断分布有没有漂移；若发现错报，改 `params.json` 关掉 `report_tags` 即可。

## 四、比赛期提交方案（3 天 × 10 批）

**版本策略**：全部 30 批交同一个主版本，只在诊断发现问题时切换到备用版本；不混入扰动变体。

**第一批（10-04 16:00 UTC 一开赛就交）看什么**：
1. `termination_reason`：应为 `survey_complete`。`agent_error`/`agent_initialization_error` → 看 stderr 末尾 traceback（协议不匹配就热修复 main.py）；`global_wallclock_expired` → 立即换 PyPy 版本或 `params.json` 把 `plan_every_seconds` 设 3600、`rollout_k` 设 1。
2. `plan #1 [numpy]` 还是 `[python]`：后者说明 build 没装上 numpy，看 build 日志；若 `decisions=100 wall=` > 60 秒（本地纯 Python 是 54 秒）就换 PyPy 版本。
3. `decisions=100 wall=…s cpu=…s`：本地 CPython+numpy 参照 24 秒；wall/cpu 之差就是往返 + runner。wall 超过 70 秒（≈ 3×）时降级几乎必然触发，考虑换 PyPy 缩小自己那部分；若差值主要是往返，换镜像无用，只能问主办方。
4. 有没有 `projected … > …%` 行；有则核对完成数与罚分。
5. 罚分：`required_miss`、`invalid_action`、`unsafe_observation` 应全为 0；`fault_correct_reports` = 1、`fault_misreports` ≤ 1；标签 correct ≫ wrong。某场 wrong ≥ 3 → 分布漂移，改 params 关 `report_tags`（−150/次的漏洞比 +100/次的收益重要）。
6. 原始分与校准分：反推参考算法平均 = W + (原始 − W)·10000/校准；若它接近 原始/1.07，参考 ≈ kit 基线；明显更高说明参考更强，只影响绝对值。
7. 一批的排队 + 运行耗时，用来安排后续节奏。

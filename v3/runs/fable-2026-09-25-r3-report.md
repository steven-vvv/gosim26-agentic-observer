## 1. 总体判断

**位置。** obs16 在 46 场上比 kit 基线高约 7.3%（obs14 +7.18%，obs16 再 +0.12%），比"全知可行排程"低 **3.29%**（46 场逐场 0.50–6.87%，标准差 1.6），比完美信息上界低 9.97%。用基线当参考算法的校准分约 10,640，单批标准差约 89，30 批取最好期望约 +170。

**差距几乎全是信息差，但有一个可以拿回来的大项。** 3.29% 的分解（第 2 节问题 1）与各类信息价值的估计（每格天气 ≈1.7%、天气中断 ≈0.9%、隐藏标签 0.17%、故障时机 0.3–0.5%）加起来就是整个差距，说明"对偶价格 + 贪心 + 推演"这一算法类在现有信息下已接近天花板。**但**离线试验台一直假设在线层能看到仪器效率，而快照里没有效率：寒潮期（每场约 14% 的曝光、效率乘数均值 0.76）在线估值被系统性高估 1/0.76，"现在拍 vs 留到将来"的比较失真。离线复现这一盲区代价 **−0.65%**（6 场，−0.04% ~ −0.99%）；本轮在真实系统里加上在线寒潮效率修正（`fc2cold`），**23 场相对 obs16 +0.565%（标准误 0.088，21/23 场变好）**，基础分 +686、覆盖 +323、完成天区 +5.7/场。这是本轮找到的最大单项，也是自 obs11（+0.37%）以来最大的一项。

**还有多少空间（估计）。** 把可做项加总：寒潮在线修正 +0.5~0.6%，预报按生成器模型处理 +0.05~0.1%，规划器多迭代/细时段 +0.1%（离线 +0.2~0.3%，真实系统未验证），预报条件化的中断规避 +0.03~0.08%，故障期天区复拍 +0.05~0.1%。合计约 **+0.7~1.0% 原始分 ≈ +70~100 校准分**，其中约六成集中在第一项。之后剩下的都是 ≤0.1% 的碎项，单项验证成本已高于收益，只适合打包验证。

**依据可信度。** fc2cold 的 +0.57% 有三重印证：离线机理（效率盲区 −0.65%，修正后回到 −0.01%）、真实系统 23 场 6 个标准误、分项集中在基础分与覆盖（不是标签或罚分的噪声）。其余各项是估算，标注了依据。

## 2. 六个问题的结论

### 问题 1：剩余差距的分解

46 场 obs14（=obs13-cf，与 obs15 逐位相同）对比全知可行排程（`results/upper_bound/*.json` 的 `primal`，已把我们的请求奖励加回去以便可比），每场均值：

| 分项 | 全知 − obs14（分/场） | 占总分 | 说明 |
|---|---|---|---|
| 基础科学分 | +4,131 | +2.14% | 每块天区 107.2 → 110.5（+3.1%），完成数几乎相同（+1.5 块） |
| 档位加成 | +2,147 | +1.11% | 加成/基础 0.176 → 0.187：全知知道哪些时隙是 DARK |
| 覆盖奖励 | +367 | +0.19% | 全知均匀度反而更低（0.857 vs 我们 0.877），覆盖差来自基础分更高 |
| 标签 | +337 | +0.17% | 全知知道隐藏标签 |
| 罚分 | −636 | −0.33% | 全知贪心会漏 REQUIRED（我们零缺失）；剔除后真实差距约 3.6% |
| **合计** | **+6,375** | **+3.29%** | 本地 3.20 / 蒙特卡洛 a 3.37 / b 3.30 |

时间账（obs16 46 场均值）：观测 287.8 小时（1,229 次），等待 41.3 小时（175 次，全部发生在闭站期、不可避免），**中断 18.6 次浪费 2.67 小时 = 观测时间的 0.93%**。中断按原因分：背景关闭 12.7 次 / 6,551 秒（马尔可夫、无记忆，不可预报）；有预报且 P(闭站)>0.3 的降雨 3.17 次 / 1,614 秒；P∈(0.1,0.3] 0.54 次 / 329 秒；P<0.1（漏报或时间误差）1.52 次 / 770 秒。

故障（46 场）：故障必然在第 13–16 夜开始（生成器把它放在巡天中点 ±80 时隙，中位第 14 夜），检出延迟中位 2.9 小时、均值 9.5 小时。检出前在故障区完成 1.2 块 / 损失 55 分（0.03%）；检出后到平台回执（1 天）2.3 块 / 109 分（0.06%）；回执后到修复（2 天）**16.5 块 / 反事实损失 1,447 分（0.75%）**——这些是明知乘数 0.56 仍选的高价值天区（满效率约 200 分/块，平均天区 107），属于理性权衡，不是漏洞；可挖的是修复后复拍（见问题 4）。

**信息差 vs 算法差：**
- 信息差（在线拿不回）：每格天气好坏与关闭时刻 ≈1.7%（离线完美预报）、中断 ≈0.9%、标签 0.17%、故障时机 0.3–0.5%（全知排程假设故障一开始就修复计时）。这四项之和 ≈3.1–3.3% ≈ 整个差距。
- 算法差（拿得回）：主要是**效率盲区**——离线 −0.65%，真实 +0.57%（fc2cold）。它没出现在上面的加法里，因为离线"完美预报 1.7%"的对照组在线层看得见效率，而真实 agent 看不见；把它算进去后剩余的算法差约为零（±0.3%）。
- 预报能兑现的信息差上限：规划器读真实事件 +0.49%，现在兑现 0.12%，改进后（fc2）约 0.18%（相对 obs14）。

### 问题 2：预报的正确用法

先说生成器（`kit/challenge/weather_simulator.py`）里对决策有用的事实，46 场全部验证：

1. **概率字段不表示会不会发生，只编码提前量**：真事件预报的 probability = 0.52 + 0.43·closeness ± 0.035（closeness = 1 − 提前量/7 天）。凡不是假警报的预报，对应事件**必然发生**；"漏报 12%"是事件根本没有预报，不是预报错了。
2. **时间误差就是给出的 uncertainty**：真事件 σ = 提前量的确定函数（提前 0 天 900 秒，3.5 天 8,100 秒，7 天 15,300 秒），起止各自独立加噪声。
3. **假警报特征鲜明**：每场 6 条，probability ~U(0.25, 0.7)，uncertainty 恒为 7,200 秒，在事发前 2–7 夜签发，持续 1–8 小时。真事件每夜都有新修订，所以每周发布时真事件的 `issued_at_utc` 等于发布时刻，假警报的早于发布时刻。
4. 统计规则"|prob − 期望| > 0.12 或 |unc − 期望| > 900 秒 或 签发早于发布 1 小时以上"：**假警报识别 220/221，真事件误判 1/1196**（只用前两条：215/221，0/1196）。
5. **`event_id` 字段本身带 `FP` 前缀**，这是标签泄漏。建议**不要利用**（规则 8.3"发现平台缺陷请报告主办方而非利用"），可以在赛前报告主办方；上面的统计规则不依赖它，并且当 ≥80% 预报都被判为假警报（平台生成器不同）时自动退回按原概率使用，最坏退到 obs15 的水平（−0.12%）。

**现行实现的问题**：标定表把假警报和真事件混在一起拉平；p·Φ·Φ 里的 p 把反应强度打了 0.5–0.95 折；6 条假警报各自扭曲 1–8 小时窗口的容量或质量。逐时隙开放概率在有信息时隙上的 Brier 分数 0.179 → 0.156（生成器模型），寒潮夜误判 29 → 18（命中 171、漏 49 不变）。

**该用在哪里（按价值排序）：**

| 用处 | 判断 | 依据 |
|---|---|---|
| **在线估值：寒潮期效率乘数** | **最大，+0.5~0.6%** | 站点可观测却有生效事件 ⇒ 只可能是寒潮；乘数用同一事件此前读数的中位数/0.95 估计，读数不足 3 个时用预报 severity（1 + sev·(0.68−1)），再没有用 0.75。fc2cold 23 场 +0.565%（0.088） |
| 规划器容量与质量：滤假警报、真事件概率记 1、开放率 = 0.931 × Π(1 − 处于事件内的概率) | 小正，+0.05~0.1% | fc2 32 场相对 obs16 +0.066%（0.040），21/32；相对 obs14 +0.180%（0.056） |
| 跨时隙曝光被打断的风险（`closure_risk` 机制已有，把常数 1.4% 换成预报条件化的 P(下一时隙闭站)） | +0.03~0.08% | 可预报中断浪费 1,614 秒/场 = 观测时间 0.16%；P>0.3 的时隙 68% 确实闭站（3,305 闭 / 1,578 开），每场约 106 个这类时隙；无条件版本曾 −0.08%，条件化后才可能为正 |
| 规划器知道寒潮时段 | ≈0 | 离线 plancold −0.11%（噪声内）；旧笔记 +0.08%。价值在在线层，不在规划层 |
| 读数"干净"的判定（`_under_cold_wave` 用滤掉假警报的预报） | ≈0 | 75% 读数走精确路径，不看 clean |

推演层（60 分钟持续当前天气）不必改：时隙级 AR(1) 0.88，一小时内持续性假设合理；档位选择上限只有 0.03–0.05%。

### 问题 3：更多算力能换来什么

离线试验台（`tools/plan_experiment.py` 的复制驱动 `offline_driver.py`，6 个本地场景，基准 = 1 小时时段、每小时重规划、规划内覆盖）：

| 变体 | 相对基准 | 场数 | 逐场 |
|---|---|---|---|
| 迭代 ×4（1200/600） | **+0.30%**（sd 0.16） | 5 | +0.01 ~ +0.45 |
| 30 分钟时段 + 迭代 ×4 | +0.19%（sd 0.10） | 5 | +0.03 ~ +0.32 |
| 每 30 分钟重规划 | +0.09% | 5 | 真实系统已采用（+0.11%） |
| 推演 (5, 60 分钟) | +0.23% | 5 | 真实系统已采用 |
| **精确 LP 对偶（HiGHS，每次重规划）** | s101 −0.17%，s201 +0.04% | 2 | 每场 513–652 秒 vs 30 秒 |
| 在线看不到效率（effblind） | −0.65% | 6 | 见问题 2 |

判断：
- **精确 LP / 最小费用流：不做。** 收敛到精确对偶没有额外价值（两场 ≈0），150 次次梯度的"欠收敛"甚至可能是有益的正则化。
- **多迭代（×4）：值得一次真实系统试验**，离线 5 场全部非负、均值 +0.3%，但离线 0.2% 量级的结论曾在真实系统翻车（持续性 +0.19 → −0.23）。改参数即可（`plan_first_iterations` 1200、`plan_iterations` 600）。代价是平台 CPython+numpy 规划 84 秒 → 约 340 秒，加上 obs16 事件开销总计约 700 秒/3600，可接受；纯 Python 回退会到约 2,600 秒并触发降级，所以只在 numpy 路径下启用（按 `np is not None` 分档）。细时段（30 分钟）离线不比只加迭代好，且规划成本再翻倍，暂不做。
- **每次决策重规划 / MPC 把规划器放进推演环**：不做。20 分钟重规划 +0.008%，推演 90 分钟 −0.075%，推演候选 8 名 +0.003%，全部饱和。
- **按天气情景采样的随机规划**：不做。夜级 AR(1) 0.82 的可预测性已被"持续性"试验测过（真实 −0.23%）；档位非线性已由分位数积分 g(q) 处理；情景采样只会引入噪声。
- Rust/numpy 提速本身不产生分数，只对平台耗时风险有意义；如果做，价值在"允许迭代 ×4 和更宽的时间保护余量"。

### 问题 5：30 批取最好 + 校准分下的取舍

结论不变：**只优化均值，不做方差工程**，但依据更新：
- 我们自己的轨迹噪声每场 sd 0.13–0.20%，两场一批约 10–15 校准分，叠加到种子噪声 89 上对 E[max of 30] 只多 1–2 分；要靠"抬方差"多拿 10 分需要 σ≈44 分的零均值噪声，没有这样的杠杆。
- **按开局状态切换参数**：用 13 个已有变体检验，逐场增益与可观测状态（故障乘数、场景总分）的相关 |r| ≤ 0.3，且所有变体均值都 ≤ 基准，没有任何"在某类状态下更好"的备选参数可切。
- 校准分与故障乘数正相关（+0.27）是结构性优势（kit 参考算法检测不到温和故障），不需要动作。
- 真正"状态相关"的改进是 #1 寒潮修正——它按状态调整估值，提高均值而非方差。

### 问题 6：验证方法

噪声结构（46 场）：
- 变体相对单次 obs14 运行的逐场差异 sd 0.18–0.37%（evfc 0.32、ev1200 0.30、ro5400 0.37、req 0.18）→ 46 场标准误约 0.044%。
- **13 个变体的逐场差异两两相关 +0.6 ~ +0.9**：相对同一次 obs14 运行比较时，obs14 自身那次轨迹的运气是所有比较共享的分量（4 场 × 8 个中性扰动测得：单次运行轨迹噪声 sd 0.13%，基线偏离扰动均值 rms 0.20%）。
- 样本量：单侧 5%、功效 80%，检出 Δ=0.1% 需要约 55 场，Δ=0.05% 约 220 场；92 场标准误 0.031%。

建议：
1. **再生成 46 个蒙特卡洛场景**（`tools/mc_scenarios.py --base data/scenarios/eval-a --prefix mc-a --seeds 9117..9132`，eval-b 同理），成本几乎为零，把标准误压到 0.03%。
2. **建一个参考集合**：obs16（或采用后的 obs17）× 3–4 个中性扰动跑满全部场景，之后所有变体与"扰动均值"比较——共享分量约占方差六成，k=4 时等效样本量约 ×1.8；一次性 2–3 小时机时，可复用。候选变体之间也直接两两配对比较（sd 约 0.77 倍）。
3. **两段式**：先离线试验台（30–45 秒/场；本轮它把效率盲区 −0.65% 预测对了）筛 ≥0.2% 的结构改动，再进真实系统；0.1% 以下的项只打包验证。
4. 每次都看 agent.log 里的静默退化（`weather events disabled`、`forecasts look false; using raw probabilities`、`projected … planning off`），并报分项（基础/加成/覆盖/标签/罚分/天区数），只看总分会把机制性收益和噪声混在一起。
5. 采用/放弃判据：23 场后均值 ≤0 → 放弃；46 场均值 ≥ +0.05% 且 ≥60% 场变好 → 采用；介于其间补到 92 场。

## 3. 行动清单（按 期望增益 ÷ Token 成本 排序）

1. **移植 `cold_online` 到工作副本（→ obs17 候选）。** 把 `agent-fc2cold/policy.py` 里的 `_cold_factor`、`self.cold_factor` 及 `_choose/_refine/_rollout` 三处乘法搬进 `agents/observer/policy.py`（约 40 行）；估计乘数时排除疑似/已确认故障区的读数；加单元测试"无寒潮时与 obs16 逐位相同"。验证：已有 23 场，补齐 46 场 + 新 46 场蒙特卡洛；消融三组——只 cold_online（`fc_model: table`）、只 fc2、两者都开；看基础分与覆盖分项；均值 ≥ +0.3% 且 ≥70% 场变好即采用（当前 +0.565%，21/23）。同时用官方 runner + CPython 3.12 + numpy 跑一场确认耗时不变（`_cold_factor` 每次决策 O(预报条数)）。

3. **规划器迭代 ×4 试验。** `params.json` 设 `plan_first_iterations: 1200, plan_iterations: 600`，仅 numpy 路径生效；46 场看均值（离线 +0.3%，真实系统预期 +0.1%），同时用 CPython+numpy 跑一场确认 `plan=` 累计秒数 < 400。若真实系统 ≤ +0.05% 则放弃，不再碰细时段。
4. **预报条件化的中断风险。** 在 `_risk_adjust` 里把常数 p 换成 `1 − planner._site_open(下一时隙中点)/0.931`（无预报时 ≈ 背景 1.35%），`closure_risk` 只在 p > 0.1 时参与精算与推演第一步。验证：46 场，看 `weather_interrupted` 次数与浪费秒数（目标从 1,614 秒/场压掉一半）以及总分；≤0 放弃。
5. **故障期天区复拍纳入规划。** `Planner.replan` 增加 `banked` 参数：对已完成但 `banked_base/满效率估值 < 0.8` 的天区加入 rows，时段价值 = 满效率价值 − 已入账（覆盖项只算 w·E·Δ基础分）。先在离线试验台加一个故障期折价的模拟验证方向，再进真实系统。
6. **验证设施**（与 #1 并行）：生成 46 个新蒙特卡洛场景；跑 obs16 × 3 个中性扰动做参考集合；把 `compare.py`（支持同时对 obs14 与 obs16 比较并输出分项）收进 `tools/`。
7. 不做：精确 LP、MPC、更深推演、随机规划、持续性、覆盖投影（除非先离线证明）、等待博弈、REQUIRED/FLEX 风险、请求、新星复拍。
